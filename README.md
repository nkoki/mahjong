# 麻雀点数計算アプリ（4人打ち・3人打ち）

4人打ち・3人打ちのリーチ麻雀の **点数計算・対局管理・戦績記録** を行う Flutter アプリです。

- フレームワーク: Flutter 3.22 以上 / Dart 3.4 以上
- 状態管理: Riverpod（`flutter_riverpod`）
- 対応: Android / iOS（確認用に Web も同梱）

## 実行方法

Flutter SDK のインストールと PATH の設定が必要です（`flutter --version` で確認できます）。
PowerShell でも動くように、1行ずつ実行してください。

```bash
git clone https://github.com/nkoki/mahjong.git
cd mahjong
flutter pub get
flutter run -d chrome   # Chrome で起動（スマホのエミュレータ・実機なら flutter run）
flutter test            # アプリのテスト（対局進行・保存・画面操作）
cd packages/mahjong_score_engine
dart test               # 点数計算エンジンのテスト
```

### 画面の見た目のテスト（ゴールデンテスト）

`test/golden/` は、主な画面（ホーム・対局画面（明るい／暗い）・和了入力・計算結果・戦績詳細・個人成績・卓に置く表示）の画像を
`test/golden/goldens/` に保存しておき、`flutter test` のたびに今の画面と比べるテストです。画面を変えると失敗するので、
意図した変更なら次のコマンドで画像を作り直し、作り直した画像を目で確かめてからコミットしてください。

```bash
flutter test --update-goldens test/golden
```

- テストでは文字が四角で描かれます（Flutter のテスト用のフォント）。配置・色・大きさの変化を見るためのものです。
- Flutter の版が変わると描き方がわずかに変わることがあるので、画素の1%までの違いは同じとみなします（`test/golden/flutter_test_config.dart`）。

### Web 版をブラウザで動かして確かめるテスト（E2E）

`e2e/smoke.mjs` は、ビルドした Web 版を実際のブラウザ（Chromium）で開き、新規対局 → 和了（翻・符で入力）→ 流局の画面 → 戦績・個人成績 → プライバシーポリシーのページ、と操作して確かめるテストです。
GitHub Actions では Web 版のビルドのあとに動かし、失敗したら公開しません。想定していない外部のサイトへの接続があっても失敗にします
（今は日本語のフォントを読み込む Google Fonts だけ）。

```bash
flutter build web --release --no-web-resources-cdn --base-href /mahjong/
mkdir -p /tmp/site && cp -r build/web /tmp/site/mahjong
(cd /tmp/site && python3 -m http.server 8765 &)
cd e2e
npm ci
npx playwright install chromium
node smoke.mjs http://localhost:8765/mahjong/
```

- Flutter の Web 版は画面を canvas に描くので、読み上げ用の情報（セマンティクス）を有効にしてから、ボタンなどを名前で探して操作します。
- Web 版は描画エンジン（CanvasKit）も GitHub Pages から配信します（`--no-web-resources-cdn`）。日本語のフォントだけは Google Fonts から読み込みます（プライバシーポリシーにも記載）。

### Android の署名の鍵を作る

鍵（`.jks`）と `key.properties` はリポジトリに入れません（`android/.gitignore` で除外済み）。**鍵とパスワードを失くすとアプリを更新できなくなる**ので、安全な場所に保管してください。

```bash
keytool -genkey -v -keystore ~/mahjong-upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

`android/key.properties` を作り、次のように書きます。

```properties
storePassword=（鍵を作るときに決めたパスワード）
keyPassword=（同上）
keyAlias=upload
storeFile=/home/あなた/mahjong-upload.jks
```

```bash
flutter build appbundle   # Google Play に出すファイル（build/app/outputs/bundle/release/app-release.aab）
```

## Web 版の公開（GitHub Pages）

`main` に push すると、GitHub Actions（GitHub が自動で処理を実行する仕組み）が `.github/workflows/deploy-pages.yml` に沿って、
テスト → Web 版のビルド → GitHub Pages への公開を行います。公開先は `https://nkoki.github.io/mahjong/` です。

- 初回だけ、GitHub のリポジトリの **Settings → Pages → Build and deployment → Source** を **GitHub Actions** にしてください。
- 非公開（Private）のリポジトリで GitHub Pages を使うには、有料プラン（GitHub Pro など）が必要です。
- テストが失敗した場合は公開しません（前回公開したものがそのまま残ります）。
- iPhone で使うときは、Safari で開いて共有ボタンから「ホーム画面に追加」すると、アプリのように起動できます。
  ホーム画面から使わないと、7日間開かなかったときに Safari が保存データを消すことがあります。

## 機能

| 機能 | 内容 |
|---|---|
| ルール設定 | ホーム画面右上の調整アイコンから開く。持ち点・返し・ウマ・トビ・半荘／東風の初期値と、喰いタン・切り上げ満貫・数え役満・ダブル役満・連風牌の雀頭の符・ダブロン・和了止め・西入（南入）・包・流し満貫・途中流局・赤ドラを設定できる。保存したルールはこれから始める対局に使われ、対局ごとに記録される（対局中・終わった対局のルールは変わらない） |
| 3人打ち | 新規対局画面で「4人打ち／3人打ち」を選べる。3人打ちは二萬〜八萬なし・チーなし・東1〜3局と南1〜3局。北抜き（抜きドラ）あり／なし、ツモ損／折半を選べる。ルール設定は4人打ち用と3人打ち用を別々に保存 |
| プレイヤー名の候補 | 新規対局画面の名前の欄を押す（または欄の右の ▼ を押す）と、過去に入力したことのあるプレイヤーの名前（最近使った順・すべて）が一覧で開き、選ぶとその欄に入る。欄に文字を入れると、その文字を含む名前（部分一致。大文字・小文字、ひらがな・カタカナの違いは無視）に絞り込める。ほかの欄に入っている名前は一覧に出さない。欄を押すまでは一覧は出さない。「前回のメンバー」で同じ人数の前回の対局の4人（3人）を座順のまま入れられる。名前の欄は空のまま始めると「プレイヤー1」などになり、それは候補に出さない。同じ名前の人が2人いると開始できない（個人成績を正しく集計するため） |
| 新規対局 | 4人の名前、対局の長さ（一局精算／東風戦／半荘戦／一荘戦）、持ち点（配給原点）、返し、ウマ、トビの有無。持ち点・返し・ウマは、よく使う値のボタンのほかに、テキストボックスで自由な値も入力できる（持ち点・返しは100点単位、ウマは1位〜4位を千点単位で、合計0） |
| ダッシュボード | 現在の局・本場・供託、4人の点数・自風・順位・トップとの差、立直の宣言／取消、1つ前に戻す |
| 祝儀（チップ） | ルール設定の「祝儀（チップ）を記録する」をオンにすると（初期値はオフ）、計算結果画面で和了者ごとに祝儀の枚数を入れられる。手牌で入力したときは赤ドラ・裏ドラ・一発の数を目安として最初から入れる（翻・符で入力したときは0枚から）。ロンは放銃者が、ツモはほかの全員がその枚数ずつ払う。戦績詳細・個人成績・CSV（対局一覧）に祝儀の合計を表示。局の修正では祝儀の枚数は変えられない |
| 焼き鳥・トビ賞 | ルール設定の「ローカルルール（精算ポイント）」で、焼き鳥（1回も和了しなかった人が払う）とトビ賞（飛んだ人が飛ばした人に払う）を なし・5P・10P・20P から選ぶ（初期値はなし）。終局したときの最終ポイントに足し引きし、結果画面・戦績詳細に「焼き鳥・トビ賞 ±P」と表示（個人成績・CSV のポイントにも含む）。焼き鳥は和了した人で等分し、全員和了・誰も和了しなかったときは動かない。和了者を記録していない古い局がある対局では数えない。トビ賞は「トビあり」のときだけで、最後の局の和了者（ダブロンなら等分）がもらう。流局・チョンボで飛んだときは動かない |
| ルールのセット | ルール設定の「今のルールをセットとして保存」で、ルール（持ち点・ウマ・詳細ルールすべて）に名前を付けて保存できる（4人打ち・3人打ちは別。全部で20個まで。同じ名前なら上書き）。ルール設定でセットを押すと読み込み、× で削除。新規対局の画面で選ぶと、その対局のルールが切り替わる |
| 卓に置く表示 | 対局画面のメニューの「卓に置いて表示」で、スマホを卓の真ん中に置いて全員が自分の向きで読める表示に切り替える。卓ビューと同じ卓の形で、4人（3人）それぞれの席（名前・点数・順位・立直の千点棒）をその人に向けて回して表示し、真ん中の窓に局・本場・供託を表示。各席の「立直」「和了」をこの表示のまま押せる（和了はその人を和了者にして和了入力を開く）。下のボタンで流局・1つ前に戻す・回す（手前に座る人を変える）・閉じる。3人打ちは北の席が空く。終局後は立直・和了は押せない |
| 画面を消さない | 対局中（対局画面を開いている間）は画面が自動で消えない。対局画面のメニューの「対局中は画面を消さない」でオン／オフでき、設定は端末に保存（初期値はオン）。終局したり対局画面を閉じたりすると元に戻る。`wakelock_plus`（BSD-3-Clause）を使用 |
| 和了入力 | 和了者・ロン／ツモ・放銃者、手牌（牌パレットで入力）、和了牌、鳴き（チー・ポン・明槓・加槓・暗槓、赤5指定可）、ドラ表示牌・裏ドラ表示牌、状況役（立直・ダブル立直・一発・嶺上開花・槍槓・海底・河底・天和・地和） |
| 牌の見た目 | 牌は画像を使わず図形と文字で、本物の牌に近い見た目に描く（`lib/shared/widgets/tile_painter.dart`）。白い面の下に背の色を見せて厚みを出し、筒子は決まった並びの二重の輪（一筒は大きな飾りの丸）、索子は節のある竹（一索は鳥、八索は M 字）、萬子は漢数字と赤い「萬」、字牌は東南西北が黒・發が緑・中が赤・白は青い枠、赤ドラは赤い5。読み上げ（スクリーンリーダー）には「5萬」「赤5筒」のような名前を付ける |
| 翻・符で入力 | 和了入力画面の「翻・符で入力」に切り替えると、手牌を入れずに翻数（ドラ・赤ドラ・裏ドラ・抜きドラ込み、1〜13翻以上）と符（20〜110符）、または役満（二倍・三倍役満）を選ぶだけで点数を計算できる。選ぶと画面の下に点数の見込み（例: 子のロン 5200点、2600オール）を表示。最後に選んだ入力方法（手牌／翻・符）を覚えていて、次に和了入力を開いたときも同じになる。本場・供託は自動で加える。20符は平和ツモ、25符は七対子のみ（どちらも2翻以上）で、ありえない組み合わせは選べない。包（責任払い）は、どの役満か分かる手牌での入力のときだけ選べる。ダブロンで1人は翻・符、もう1人は手牌で入力することもできる |
| よく使う点数のショートカット | 翻・符で入力するとき、画面の上の「よく使う」に、最近入力した手（新しい順に4つまで。時計の印付き）と、よく出る手（1〜3翻30符・40符、満貫、跳満、倍満）を点数付きで並べる（例: 3翻30符 3900）。点数は選んだ和了者（親・子）とロン・ツモに合わせて変わる。押すだけで翻・符が入る |
| ダブロン | ロンの計算結果画面から「ダブロン：もう1人のロン和了を入力」で2人目を入力し、2人分をまとめて確定できる（放銃者・和了牌・ドラ表示牌は1人目と同じものが入る）。トリロン（3人）は流局の「三家和」として扱う |
| 計算結果 | 役一覧と翻数、符の内訳、満貫などの名称、点数（例: 1300-2600 / 4000オール）、全員の点数移動（本場・供託込み） |
| チョンボ | 対局画面のメニュー「チョンボ（錯和）を入力」から、した人を選んで罰符を入れる。満貫払い（子は親に4,000点・子に2,000点ずつ、親は全員に4,000点ずつ。3人打ちも同じ額ずつ）。その局は同じ本場でやり直し、その局で出した立直棒は本人に戻す（前の局から持ち越した供託はそのまま）。和了止めにはならない。戦績・CSV に「チョンボ」として残り、個人成績にチョンボの回数を表示（和了率などの局数には含めない） |
| オーラスの条件 | オーラス・延長戦では、対局画面の帯「オーラスの条件（トップになるには）を見る」から、トップ以外の人がトップになるのに必要ないちばん安い和了を、ロン（トップ以外から）・直撃（トップから）・ツモ別に表示（例: 3翻40符（5200））。本場・供託を含めて計算し、同点は起家に近い人が上位。よくある手（40符まで・満貫以上）で示し、符の高い手でもっと安く届くときは「符が高ければ 2翻70符（1200-2300）でも届く」と添える。役満でも届かなければそう表示。流局のテンパイ料での逆転は含めない |
| 点数早見表 | ホームの「点数早見表」で、1〜4翻 × 20〜110符のロン・ツモの点数と、満貫・跳満・倍満・三倍満・役満の点数を一覧で表示。子・親、4人打ち・3人打ちを切り替えられる。ルール設定の切り上げ満貫・3人打ちのツモ損/折半・数え役満に従って計算し、満貫になるマスは色を付ける。3人打ちでは、ツモで受け取る合計（例: 計6,000）も表示し、ツモ損・折半をその場で切り替えて比べられる（ツモ損は1人が払う額が4人打ちと同じで、北家の分が無いぶん合計が少ない。ロンは4人打ちと同じ）。20符はツモだけ、25符は2翻から（無い組み合わせは「—」）。本場・供託は含まない |
| 点数計算の練習 | ホームの「点数計算の練習」で、でたらめに作ったあがり形（手牌・和了牌・鳴き・ドラ表示牌、場風・自風・ロン／ツモ・立直）を見て、点数を4つの選択肢から選ぶ。答えると正解・不正解と、翻・符・役・符の内訳を表示。正解数と連続正解数を表示する。点数はルール設定（4人打ち）に従う。鳴きは1つまでで、赤ドラ・槓・役満は出ない |
| 流局入力 | 荒牌平局（ノーテン罰符）、流し満貫、九種九牌、四風連打、四家立直、四開槓、三家和。途中流局は親の連荘・本場+1で、供託は持ち越し。四家立直は全員が立直しているので、アプリで立直を押していない人からも供託を1本（1,000点）ずつ取る（すでに立直している人からは重ねて取らない。流局の画面で誰から取るかを表示し、元に戻すと取る前に戻る） |

## 3人打ちのルール

- 牌: 萬子の 2〜8 を使わない（1萬・9萬のみ）。赤5萬なし。ドラ表示牌は 1萬→9萬、9萬→1萬
- 鳴き: チーなし
- 北抜き（初期値あり）: 抜いた北1枚につき抜きドラ1。ドラの数え方では抜いた北も「北」として数える（表示牌が西なら抜いた北もドラ）。なしの場合、北は普通の字牌
- 局数: 東1〜3局・南1〜3局（東風戦は東1〜3局、一荘戦は北3局まで）。西入ありなら西1〜3局まで
- 初期値: 35,000点持ち・40,000点返し・ウマ +15/0/-15（オカは (返し-持ち点)×3）
- ツモの支払い（初期値ツモ損）: ツモ損は北家の分をもらえない（子の満貫ツモは 親4000・子2000）。折半は北家の分を2人で分ける（親5000・子3000）
- 本場: ロン300点／ツモは各100点。ノーテン罰符: 場に3,000点
- 途中流局: 九種九牌・四開槓のみ。ダブロンは最大2人

## ルール

次のルールはルール設定画面で変更できます（括弧内は初期値）。

- 喰いタン（あり）、切り上げ満貫（なし）、数え役満（あり）、ダブル役満・役満の複合（あり）、連風牌の雀頭（4符）
- ダブロン（あり。なしの場合は頭ハネ）、和了止め（あり）、西入・東風戦は南入（なし）、包（あり）、流し満貫（あり）、途中流局（あり）、赤ドラ（あり）
- 包（責任払い）ありの場合: 大三元・大四喜の和了の結果画面で、確定させる牌を鳴かせた人を選べる。ツモはその役満の分と本場を包の人が全額、ほかの人からのロンはその役満の分を包の人と放銃者で半分ずつ（本場は放銃者）、包の人からのロンは普段どおり。ほかの役満と重なった場合、包になるのは大三元・大四喜の分だけ
- 西入ありの場合: 最終局が終わって誰も返し点に届いていなければ次の場に入る。延長中は誰かが返し点に届いた局で終了（サドンデス）し、届かなくても延長の4局目で終了。和了止めは親が返し点に届いている場合だけ。延長中は対局画面に終わる条件を表示

変更できない（固定の）ルール:

- 本場: ロン300点 / ツモ各100点、供託リーチ棒は和了者が獲得（流局時は持ち越し、終局時はトップが獲得）
- 親の和了・親テンパイの流局・途中流局は連荘（本場+1）。子の和了は親流れで本場0に
- ダブロン（ありの場合）: 放銃者が2人分の点数を払う。本場・供託は、放銃者から見て打つ順番が近い和了者が受け取る（上家取り）。和了者に親がいれば連荘
- トリロンは流局（三家和）
- 終局: 最終局が終わったとき、トビ（0点未満、設定時）、オーラスで親が和了してトップのとき（和了止めありの場合）、またはメニューから手動で終了
- 同点の順位は起家に近い人が上位
- 複数の解釈ができる手（例: 二盃口と七対子、三暗刻と一盃口、両面と嵌張）は最も点数が高いものを採用（高点法）

## データの保存について

- 保存には `shared_preferences` を使っています。保存場所は Android では SharedPreferences、iOS では NSUserDefaults、Web ではブラウザの localStorage です。
- 対局ごとに別のキー（`mahjong_session_<対局ID>`）に JSON（テキスト形式のデータ）で保存し、対局の並び順は目次（`mahjong_session_index`）に保存します。
- 対局の状態が変わるたび（立直・和了・流局・元に戻す・削除など）に、**変わった対局だけ**を自動で保存します。何百対局あっても、1回の保存は対局1つ分（約5KB・1ミリ秒未満）で済みます。
- 「元に戻す」の履歴（直近10回分）には、局ごとに変わる値（点数・局・本場など）と「局の記録は何局目まで」という件数だけを保存し、局の記録の文章は1回だけ保存します。
- 容量の目安: 1対局（半荘・12局程度）で約5KB、100対局で約0.5MB です。Web の localStorage の上限（約5MB、ブラウザによって違う）に近づくのは800〜1,000対局くらいからです。
- 保存データにバージョン番号を付けているので、将来データの形を変えるときに移行できます（現在は version 9。全対局を1つにまとめて保存していた以前の version 1・2 のデータは、起動時に自動で新しい形に移します）。
- version 4 で、局の記録に和了者・放銃者・立直した人・和了点を加えました（個人成績の集計用）。version 3 のデータもそのまま読めますが、その局にはこれらの記録が無いので、個人成績の和了率・放銃率・立直率・平均打点には含みません。
- version 5 で、ルールに「祝儀を記録するか」、局の記録に祝儀の増減を加えました。version 4 以前のデータは祝儀なしとして読み込みます。
- version 6 で、ルールに焼き鳥・トビ賞（精算ポイント）を加えました。version 5 以前のデータはどちらもなしとして読み込みます。
- version 7 で、対局の途中のプレイヤーの交代を加えました。version 6 以前のデータは交代なしとして読み込みます。
- version 8 で、局の記録に和了の役を加えました（個人成績の役の出現回数用）。version 7 以前に記録した局は、役の出現回数に含めません。
- version 9 で、ルールに対局の長さ（一局精算・一荘戦）を加えました。version 8 以前のデータは、東風戦・半荘戦の設定からそのまま読み込みます。
- 保存データが壊れていて読み込めない場合も、アプリは落ちずに起動します。壊れているのが一部の対局だけなら、その対局以外はそのまま読み込みます。壊れたデータは消さずに `mahjong_corrupt_` で始まる別の名前で残します。目次が壊れた場合は、対局データから作り直します。
- アプリをアンインストールしたり、ブラウザのサイトデータを消したりすると、保存データも消えます。備えとして、バックアップ画面から全対局をファイルに書き出せます。
- 保存するのは**最新100対局まで**です。100件を超えると、新しい対局を始めたときに、**お気に入り（★）にしていない一番古い終局済みの対局**から自動で削除します。削除する前に、どの対局が消えるかを確認画面で表示します。
  - お気に入りの対局と対局中の対局は削除しません。それらだけで100件を超えた場合は、100件を超えて保存します。
  - 戦績一覧には「保存中: ○ / 100件」と、次に削除される対局の印を表示します。
- Web 版はブラウザの容量の上限（約5MB）があるので、その50%を超えるとホーム画面で警告します。
- 保存に失敗したとき（容量不足など）はどの画面でもお知らせし、ホーム画面にも表示し続けます。読み込めなかったデータがあったときもホーム画面でお知らせします。

## カメラ認識について

- 撮影・写真の選択に `image_picker`、画像の縮小に `image`（MIT）、認識モデルの実行に `tflite_flutter`（Apache-2.0）を使っています。
- 認識モデルは2つです。牌の位置を見つける検出モデル（SSD、MobileNet-MultiHW-AVG、入力 384×384）と、見つけた牌を1枚ずつ見分ける分類モデル（MobileNetV3-Small、入力 縦128×横96。37種類の牌と「牌ではない」を見分ける）。牌の種類は37種類（萬子・筒子・索子・字牌の34種類＋赤5の3種類）。
- 読み取りの手順: 写真全体から牌を探す → 牌が写っている範囲だけを切り抜いてもう一度読み取る → 重なった検出を1つにまとめる（NMS）→ 見つけた牌を1枚ずつ切り抜いて大きくし、分類モデルで種類を見分け直す（写真全体を縮めると潰れてしまう萬子の漢数字などを見分けるため。「牌ではない」と答えたものは捨てる）→ 一番多く牌が並んだ列を手牌として左から順に並べる（離れた列の牌は使わない）。
- 3人打ちでは二萬〜八萬を除き、赤ドラなしのルールでは赤5を普通の5として入れます。同じ牌が5枚以上なら5枚目から除きます。
- Web 版では TensorFlow Lite を動かせないため、カメラ認識はありません（和了入力画面に「スマホのアプリ版で使えます」と表示します）。
- 以前の版で保存した Qwen の API キーは、アプリの起動時に端末から消します。
- 読み取りは間違えることがあります。入れたあとに手牌を確認してください。

### 認識モデルの作り方（`tools/tile_model/`）

商用利用できるように、AGPL のもの（Ultralytics など）は使っていません。

| 使うもの | ライセンス |
|---|---|
| 学習の道具: MediaPipe Model Maker（TensorFlow 2.15） | Apache-2.0 |
| もとにした学習済みモデル: TensorFlow Model Garden の MobileNet SSD | Apache-2.0 |
| 合成データの材料: [FluffyStuff/riichi-mahjong-tiles](https://github.com/FluffyStuff/riichi-mahjong-tiles) の牌画像 | CC0 1.0 |
| 実写データ: Roboflow Universe の2つのデータセット（下の「データの出典」） | CC BY 4.0 |
| 分類モデルの学習: TensorFlow / Keras の MobileNetV3-Small（ImageNet で学習済み） | Apache-2.0 |
| アプリでの実行: tflite_flutter | Apache-2.0 |

Python 3.11 を使います。Roboflow の API キーは環境変数 `ROBOFLOW_API_KEY` に入れておきます（ファイルには書きません）。

```bash
cd tools/tile_model
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip uninstall -y jax jaxlib   # mediapipe と一緒に入る jax は TensorFlow 2.15 の TFLite 書き出しを壊すので外す
git clone --depth 1 https://github.com/FluffyStuff/riichi-mahjong-tiles data/riichi-mahjong-tiles
python synth.py --tiles data/riichi-mahjong-tiles/Export/Regular --out data/synth --count 4000 --seed 1
python synth.py --tiles data/riichi-mahjong-tiles/Export/Regular --out data/synth_val --count 400 --seed 100
python fetch_roboflow.py --out data/roboflow
R=data/roboflow
python merge.py --out data/train --drop 0z --src data/synth $R/hust/train $R/riichi_detection/train
python merge.py --out data/val --drop 0z --src data/synth_val $R/hust/valid $R/hust/test $R/riichi_detection/valid $R/riichi_detection/test
python merge.py --out data/val_real --drop 0z --src $R/hust/valid $R/hust/test $R/riichi_detection/valid $R/riichi_detection/test
python train.py --train data/train --val data/val --out out --epochs 15 --batch 16 --fp16
python train_classifier.py --train data/train --val data/val --out out_cls_first --epochs 8   # まず「牌ではない」なしで学習
python mine_negatives.py --model out --data data/train --out data/train/negatives.json --classifier out_cls_first --trusted-prefix s0_ --skip-prefix s2_ --label-negatives $R/riichi_detection/train:s2_:0z
python mine_negatives.py --model out --data data/val --out data/val/negatives.json --classifier out_cls_first --trusted-prefix s0_ --skip-prefix s3_ s4_ --label-negatives $R/riichi_detection/valid:s3_:0z $R/riichi_detection/test:s4_:0z
python train_classifier.py --train data/train --val data/val --out out_cls --epochs 8 --negatives data/train/negatives.json --val-negatives data/val/negatives.json --plain-negatives 1500
python evaluate.py --model out --data data/val_real --save-preview preview.jpg   # 実写だけでの精度
python evaluate.py --model out --classifier out_cls --data data/val_real --two-pass --hand-rows --per-class   # アプリと同じ読み取り方での精度
python evaluate.py --model out --data data/val --dump-fixture ../../test/fixtures/tile_decode_fixture.json
cp out/tile_detector.tflite out/tile_anchors.bin out/tile_labels.txt ../../assets/models/
cp out_cls/tile_classifier.tflite out_cls/tile_classifier_labels.txt ../../assets/models/
```

- ダウンロードしたデータを読むときは、`python -I`（同じフォルダや環境変数から余計なモジュールを読まない）で動かすと安全です。スクリプトは `python -I` でも同じフォルダの `classes.py` を読めます。
- Roboflow のデータの取得には `api.roboflow.com` のほか、`app.roboflow.com`（書き出したファイル）への接続が必要です。
- 「Riichi Mahjong Detection」の `0z` は牌の裏なので `--drop 0z` で外します（外すと、牌の裏は牌として検出しないように学習します）。
- 「Riichi Mahjong (HUST)」には赤5のクラスがありません。中身を確かめたところ赤5の牌は写っていなかったので、5萬・5筒・5索は普通の5として使っています。
- `evaluate.py` は、アプリと同じ後処理（縦横比を保って縮める → アンカーで箱を求める → NMS）で、牌ごとの精度・見落とし・余計な検出・写真の牌が全部正しく読めた割合を出します。`--two-pass` でアプリと同じ2回目の読み取りもし、`--hand-rows` で写真の牌の列を1列ずつ手牌の写真のようにして測り、`--per-class` で牌の種類ごとの精度と多い取り違えを出します（例: `python evaluate.py --model out --data data/val_real --two-pass --hand-rows --per-class`）。

- `synth.py`: 牌画像を並べて、卓・照明・傾き・ぼけ・影などを変えた手牌の合成写真と、牌の位置（COCO 形式）を作ります。
- `fetch_roboflow.py`: `datasets.json` のデータセットを COCO 形式で取得します。API の情報でライセンスが CC BY 4.0 であることを確かめ、違えば止まります。出典の情報は `attribution.json` に書きます。
- `merge.py`: クラス名をアプリの牌の表記（`1m`・`5mr` など）に変換してまとめます。変換できないクラス名があれば止まるので、`--map` で対応を指定します。
- `train.py`: 学習して `tile_detector.tflite`・`tile_anchors.bin`（アンカー）・`tile_labels.txt`（クラス名）を書き出します。精度（COCO 指標）は `eval.json` に書きます。
- `train_classifier.py`: merge.py の出力の箱から牌を1枚ずつ切り抜き、分類モデル（37種類＋`--negatives` を渡せば「牌ではない（bg）」）を学習して `tile_classifier.tflite`・`tile_classifier_labels.txt` を書き出します。正解率は `eval.json` に書きます。
- `mine_negatives.py`: 分類モデルに「牌ではない（bg）」を覚えさせる例を集めます（検出モデルが間違えて見つけたもの・牌の無い所の切り抜き）。`--src` の順番でファイル名の頭に `s0_`, `s1_`, … が付くので、ラベルに漏れがないデータ（合成）を `--trusted-prefix`、ラベルの漏れが多いデータ（Riichi Mahjong Detection）を `--skip-prefix` で指定します。合成データの色の薄い「白らしいもの」は外し（白を捨てないように）、`--label-negatives` で元のデータセットのラベル（牌の背 0z）も加えます。
- `tile_crop.py`: 分類モデルに渡す画像の切り抜き方（箱を 8% ずつ広げる、横長なら時計回りに 90 度回す、縦128×横96 に縮める）。アプリの `lib/features/camera/tile_classifier.dart` と同じにしてあり、`python tile_crop.py --dump-fixture ../../test/fixtures` でアプリのテスト用データを作ります。
- `--epochs` などを変えたときは、確認用データでの精度（`eval.json`）が下がっていないか確かめてから入れ替えてください。

**現在の状態**: `assets/models/` に学習したモデルが2つ入っています。

|---|---|---|---|

- 検出モデルの確認用データでの COCO 指標（合成＋実写 566 枚）: AP50 = 0.953、AP = 0.726
- 分類モデルだけの正解率（確認用データの切り抜き 10,401 枚）: 99.88%（実写の牌 99.92%、「牌ではない」99.0%）
- アプリは、検出モデルの確信度 0.2 以上を牌の候補にし（`TfliteTileRecognizer.detectionThreshold`）、分類モデルが「牌ではない」と答えた候補を捨てます

| 〃 | 前の版（「牌ではない」なし、確信度 0.3） | 634 | 5426 | 99.69% | 99.98% | 99.67% | 0.364 | 78.9% |
| 〃 | 検出モデルだけ（確信度 0.3） | 634 | 5426 | 99.7% | 98.3% | 98.0% | 0.36 | 72% |

「実写を1列ずつ手牌の写真のようにしたもの」（`--hand-rows`）は、実写の写真の牌の列（9枚前後）を1列ずつ取り出し、まわりを写真の色で埋めて、手牌を撮ったときに近い大きさ（11〜12枚ぶんの幅）にした画像です。

- 分類モデルで萬子の取り違えがほぼ無くなり（手牌の写真に近い条件で萬子はすべて 99.4% 以上）、「牌ではない」を足したことで、トレイの空いた所などを牌と読む余計な検出がほぼ無くなりました（HUST で 1列あたり 0.129 → 0.002）。
- Riichi Mahjong Detection の写真には、ラベルの付いていない牌が写っています。それを正しく読んでも「余計な検出」と数えられるので、Detection を含む結果は実際より悪く出ます。そのため HUST だけの結果も載せています。ラベルの付いていない牌を「牌ではない」と覚えさせないよう、`mine_negatives.py` では Detection から例を集めず、ほかの実写のデータでは、先に学習した分類モデルがはっきり牌だと答えるもの（確率 0.98 以上）を外しています。
- 白（5z）は無地なので「牌ではない」と紛れやすく、合成データで白の精度が 94.0% まで下がったことがありました。合成データの紛らわしい牌の背のうち灰色のものが白とほとんど同じ見た目で、それを「牌ではない」と覚えていたためです。`mine_negatives.py` で合成データの色の薄い「白らしいもの」を外し、代わりに縁のない平らな面と本物の牌の背（Detection の 0z）を「牌ではない」に加えて、白の精度を 96.6% に戻しました（実写では白は 99.7% 以上）。牌の背（暗槓など）は白と読まずに捨てます。合成で残る白の見落とし（116 枚中 4 枚）は、強くぼけた写真で検出モデルが見つけられないものです。
- `synth.py` の紛らわしい牌の背には、色のはっきりしたものだけを使うようにしました（灰色・黒を使わず、色も濃く混ぜる）。今の検出モデルは直す前の合成データで学習しています。
- 実写の確認用データは、学習に使ったデータセットと同じ牌・同じ撮り方の写真です。ほかの牌のセットや撮り方では精度が下がることがあります。赤5は実写の確認用データに 50 個しかないので、数値はあまり当てになりません。
- アプリでは、読み取り結果の画面に「読み取りは間違えることがあるので確認してください」と表示しています。
